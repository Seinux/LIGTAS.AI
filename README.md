# LIGTAS.AI

LIGTAS.AI is an Express application with a browser-based authentication flow. Users can register, verify a Philippine mobile number with a one-time password (OTP), log in, and access a protected dashboard. PostgreSQL stores users, pending phone verifications, and server-side sessions.

## Prerequisites

Install the following software before setting up the project:

- **Node.js 20 LTS or newer**, which includes npm. Install from [nodejs.org](https://nodejs.org/), then check with `node --version` and `npm --version`.
- **PostgreSQL 14 or newer**, including its command-line tools (`psql`). Check with `psql --version`.
- **Git**, to clone the repository.

On Windows, the PostgreSQL installer from [postgresql.org](https://www.postgresql.org/download/windows/) includes pgAdmin and `psql`. During installation, note the password you set for the `postgres` database user. On macOS or Linux, install PostgreSQL using the platform's package manager or the official downloads.

## Get the project running

1. Clone the repository and enter its folder:

   ```sh
   git clone https://github.com/Seinux/LIGTAS.AI.git
   cd LIGTAS.AI
   ```

2. Install the Node.js dependencies:

   ```sh
   npm install
   ```

3. Create a PostgreSQL database. For example, connect as the PostgreSQL administrator:

   ```sh
   psql -U postgres
   ```

   Then run:

   ```sql
   CREATE DATABASE ligtas_ai;
   \q
   ```

   If `psql` is not on your Windows `PATH`, open **SQL Shell (psql)** from the Start menu instead.

4. Create a `.env` file in the project root (next to `server.js`) and set the local database credentials:

   ```dotenv
   PORT=3000
   NODE_ENV=development
   SESSION_SECRET=replace-this-with-a-long-random-secret
   TRUST_PROXY_HOPS=0
   DB_HOST=localhost
   DB_PORT=5432
   DB_NAME=ligtas_ai
   DB_USER=postgres
   DB_PASSWORD=your_postgres_password
   OTP_DELIVERY_MODE=console
   # For live SMS, use OTP_DELIVERY_MODE=semaphore and configure:
   # SEMAPHORE_API_KEY=your_semaphore_api_key
   # SEMAPHORE_SENDER_NAME=your_approved_sender_name
   ```

   Replace the session secret and database password with your own values. `SESSION_SECRET` must be at least 32 characters; you can generate one with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Keep `.env` private; it is ignored by Git. Do not reuse the example secret in a deployed environment.

5. Create the application tables by running the SQL in [Database schema](#database-schema) against `ligtas_ai`. The app creates its PostgreSQL session table automatically on startup.

6. Start the development server:

   ```sh
   npm run dev
   ```

   Or use `npm start` to start it without nodemon. Open <http://localhost:3000/register> to register or <http://localhost:3000/login> to log in. Stop the server with `Ctrl+C`.

## Database schema

The following schema corresponds to the columns read and written by `model/User.js`, `model/PhoneVerification.js`, and the authentication controller. Run this once against a **new/empty** `ligtas_ai` database. Connect to it with `psql -U postgres -d ligtas_ai`, then paste the SQL below, or run it in pgAdmin's Query Tool. This repository does not currently include a migration or schema file.

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(254) NOT NULL,
    phone_number VARCHAR(20) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    phone_verified BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX users_email_lower_unique
    ON users (LOWER(email));

CREATE TABLE phone_verifications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE
        REFERENCES users (id) ON DELETE CASCADE,
    otp_hash VARCHAR(255) NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    attempts INTEGER NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    resend_count INTEGER NOT NULL DEFAULT 0 CHECK (resend_count >= 0),
    last_sent_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Relationships and behavior:

- A user may have zero or one pending phone verification. `phone_verifications.user_id` is unique and references `users.id`.
- Deleting a user also deletes their pending verification.
- Email is unique without regard to case, and phone numbers are unique.
- Passwords and OTPs are stored as bcrypt hashes, not plaintext.
- OTP records expire after five minutes. The application tracks attempts and resends.
- Express session data is stored in the `user_sessions` table. `connect-pg-simple` creates this table when the server starts, so it is intentionally not part of the SQL above.
- Phone numbers are stored in canonical `+63...` format. Before upgrading an existing database, back it up and check whether national and international forms collide:

  ```sql
  WITH normalized AS (
      SELECT CASE
          WHEN phone_number ~ '^09[0-9]{9}$'
              THEN '+63' || SUBSTRING(phone_number FROM 2)
          ELSE phone_number
      END AS canonical_phone
      FROM users
  )
  SELECT canonical_phone, COUNT(*)
  FROM normalized
  GROUP BY canonical_phone
  HAVING COUNT(*) > 1;
  ```

  Resolve any returned duplicate groups, then normalize national-format values:

  ```sql
  UPDATE users
  SET phone_number = '+63' || SUBSTRING(phone_number FROM 2)
  WHERE phone_number ~ '^09[0-9]{9}$';
  ```

## Development notes

- The dashboard uses a fixed dark color theme so its appearance is consistent in regular and incognito/private browser windows. Keep the theme variables in `public/css/dashboard.css` as the source of truth, and do not add a `prefers-color-scheme` override unless an explicit theme switcher is implemented.
- The registration validator accepts Philippine numbers in `09XXXXXXXXX` or `+639XXXXXXXXX` format. Usernames must be 3–50 letters, numbers, or underscores; passwords must be 8–72 characters.
- In development, `OTP_DELIVERY_MODE=console` prints the OTP to the server terminal for local testing only. Console delivery is rejected in production.
- For actual Philippine SMS, set `OTP_DELIVERY_MODE=semaphore` and configure `SEMAPHORE_API_KEY` (and optionally `SEMAPHORE_SENDER_NAME`) from a Semaphore account. See the [Semaphore API documentation](https://semaphore.co/docs). No permanently free production SMS tier was confirmed; live messages may require account credits. Local console delivery is free but does not send a message to a phone.
- Registration with the same email, phone, and password resumes an existing unverified account. Resend can issue a fresh code after expiration or the five-attempt lockout, subject to the 60-second cooldown and five-resend limit.
- The server refuses to start if `SESSION_SECRET` is absent or shorter than 32 characters. When running behind a trusted reverse proxy, set `TRUST_PROXY_HOPS` to the number of proxy hops so secure production cookies work as intended; leave it at `0` for local development.
- The server checks its PostgreSQL connection before listening. If the connection fails, confirm PostgreSQL is running and the `DB_*` values in `.env` match the local database.
- Run the automated tests with `npm test`. They cover mocked registration, OTP verification/recovery/resend, login gating, phone normalization, and SMS delivery-mode behavior. Full database/session integration still requires a configured PostgreSQL database; live SMS requires a Semaphore account.

### Manual authentication smoke test

With PostgreSQL running, the schema installed, `.env` configured, and the server started:

1. Register using a valid Philippine mobile number and an 8–72 character password. In console mode, find the OTP in the server terminal.
2. Try a malformed phone number and a mismatched password confirmation; the browser should reject them. Try registering again with the same unverified account details; it should return to verification rather than creating a duplicate.
3. Verify using the OTP. Try an incorrect code, then the correct code; after five wrong attempts, resend a fresh code after the cooldown and verify it.
4. Log in with the verified account, refresh `/dashboard`, then log out. `/auth/me` should require authentication again after logout.
5. Try logging in before verifying a separate account; it should be rejected. Check duplicate email/phone registration and the resend cooldown/limit.

The smoke test checks the real PostgreSQL and browser/session integration that the automated unit/controller tests do not exercise.

## Project layout

| Path | Purpose |
| --- | --- |
| `server.js` | Express app, session setup, static files, page routes, and startup |
| `config/database.js` | PostgreSQL connection pool |
| `model/User.js` | User lookup, creation, and phone verification updates |
| `model/PhoneVerification.js` | Pending OTP persistence and rate/expiry state |
| `controller/authController.js` | Registration, login, OTP verification/resend, and logout logic |
| `services/smsService.js` | Development OTP output and Semaphore SMS delivery |
| `utils/phoneNumber.js` | Philippine mobile-number validation and normalization |
| `route/authRoutes.js` | Authentication API routes under `/auth` |
| `middleware/` | Authentication, request validation, and rate limiting |
| `test/` | Node.js automated tests |
| `public/` | HTML pages, CSS, and browser-side JavaScript |
